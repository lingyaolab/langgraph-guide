23 · 案例一：文档摘要 map-reduce

需求：把一批文档并行摘要，最后合并成一份报告。这是 Send 最典型的场景： 运行时才知道有几篇文档，不能提前画死边。这个案例把输入、并行、合并、失败隔离与测试串起来。

读完你能做到

  • 用 Send 为每篇文档启动一个并行摘要实例
  • 用 reducer 合并摘要，并保证顺序稳定
  • 让单篇失败不影响整批，最后能看出哪篇失败
  • 用假模型测试并行图，不访问网络

先说为什么：不要用 for 循环串行摘要

串行摘要的延迟是「文档数 × 单篇耗时」，并行的延迟接近「最慢的一篇」。 LangGraph 的 Send types.py:748 让每个实例只拿到自己那篇文档，互不共享临时变量，天然适合 fan-out。

案例：输入与输出

输入：[{"id": "a", "text": "..."}, {"id": "b", "text": "..."}]
输出：{
  "summaries": ["a: ...", "b: ..."],
  "errors": [],
  "report": "a: ...\nb: ..."
}

架构：三张节点，一条 fan-out

START
  → fan_out（按 docs 生成 Send）
  → summarize × N（并行）
  → merge（排序、拼报告）
  → END

装配：State 与 fan-out

from operator import add
from typing import Annotated, TypedDict

from langgraph.graph import END, START, StateGraph
from langgraph.types import Send


class State(TypedDict):
    docs: list[dict]
    summaries: Annotated[list[str], add]
    errors: Annotated[list[str], add]
    report: str


def fan_out(state: State):
    return [Send("summarize", {"doc": d}) for d in state["docs"]]


def summarize(payload: dict) -> dict:
    doc = payload["doc"]
    try:
        text = doc["text"]
        # 真实场景：调用模型；这里用截断模拟
        return {"summaries": [f'{doc["id"]}: {text[:40]}']}
    except Exception as exc:
        return {"errors": [f'{doc["id"]}: {exc}']}


def merge(state: State) -> dict:
    return {"report": "\n".join(sorted(state["summaries"]))}


builder = StateGraph(State)
builder.add_node("summarize", summarize)
builder.add_node("merge", merge)
builder.add_conditional_edges(START, fan_out, ["summarize"])
builder.add_edge("summarize", "merge")
builder.add_edge("merge", END)

graph = builder.compile()

注意 merge 只写 report，不要再写 summaries； 否则 reducer 会把已有摘要再加一遍。

失败隔离：一篇失败不拖垮整批

summarize 内部捕获异常，把错误写进 errors。 这样其他文档照常完成，最后可以只重跑失败的那几篇。 如果让异常冒泡，整个 superstep 会失败。 

def failed_docs(state: State):
    failed = {e.split(":")[0] for e in state["errors"]}
    return [d for d in state["docs"] if d["id"] in failed]

成本控制

控制点做法
并发数限制同时 Send 的数量，或分批提交
单篇长度先切块，再摘要；不要整本塞进一次调用
输出长度给摘要设最大 token
缓存同一文档 + 同一模型可缓存

陷阱与窍门

Send 的 payload 用全局 state

你会看到每个实例都处理全部文档。因为payload 不是自动切片的。改成为每篇文档单独构造 payload。

merge 又写 summaries

你会看到摘要数量翻倍。因为reducer 又合并了一次。改成merge 只写 report。

结果顺序乱

你会看到报告顺序与输入不一致。因为并行完成顺序不保证。改成在摘要里带 id，最后排序。

自检三问

  1. 为什么这个案例必须用 Send，而不是普通边？
  2. 单篇失败时，怎样让它不影响其他文档？
  3. 并行结果的顺序由什么决定？怎么保证稳定？

30 分钟动手练习

  1. 把 3 篇文档跑一遍，确认 summaries 有 3 条、report 顺序稳定。
  2. 让第二篇抛异常，确认 errors 有记录、其他两篇仍完成。
  3. 把并发限制为 2，观察总耗时与内存变化。

16 · 部署与生产：API Server、Postgres 与水平扩展

本地 graph.invoke 和生产服务之间，差的不是一条命令， 而是持久化、并发、超时、鉴权与可观测。这一章按「先起服务，再换存储，最后扩副本」推进。

  • 把 checkpointer / store 换成 Postgres，理解为什么要先 setup()
  • 说清多副本下哪些状态必须共享、哪些必须单例
  • 给服务加健康检查、超时与基本鉴权

先说为什么：图和进程要分开看

图是逻辑，进程是运行环境。你可以把一个图跑在 CLI、FastAPI、LangGraph Server 或队列 worker 里。 生产化的核心不是「换框架」，而是让图的 checkpoint、store、并发与部署形态解耦。

Postgres：checkpoint 与 store

from langgraph.checkpoint.postgres import PostgresSaver
from langgraph.store.postgres import PostgresStore

DB_URI = "postgresql://user:pass@localhost:5432/langgraph?sslmode=disable"

with PostgresSaver.from_conn_string(DB_URI) as checkpointer:
    checkpointer.setup()
    graph = builder.compile(checkpointer=checkpointer)

with PostgresStore.from_conn_string(DB_URI) as store:
    store.setup()
    graph = builder.compile(store=store)

PostgresSaver postgres/__init__.py:45 与 PostgresStore base.py:668 都需要先建表。多副本共用同一个数据库，才能共享 thread 与 store。

多副本、队列与超时

  • 多副本：checkpointer / store / 去重状态必须共享；否则同一 thread 会分裂。
  • 同一 thread 的并发请求要串行化，或返回 409；不要让两个副本同时跑。
  • 长任务走队列 / 后台 worker，HTTP 请求只负责提交与订阅。
  • 超时分三层：模型调用、节点执行、请求总时长。
  • 健康检查要区分 liveness（进程活着）与 readiness（依赖可用）。

上线前检查

  • 同一 thread 的并发是否串行？重复提交返回什么？
  • checkpoint / store 是否是共享后端？
  • readiness 是否检查数据库与表？
  • SSE 超时、反向代理缓冲、心跳是否配置？
  • 长任务是否走后台队列，而不是阻塞 HTTP？

陷阱与窍门

多副本用 InMemorySaver

你会看到请求落到不同副本时历史丢失。因为checkpoint 只在单进程内存。改成Postgres / SQLite 共享存储（SQLite 不适合多副本）。

同一 thread 并发提交

你会看到状态互相覆盖或重复执行。因为没有会话级串行。改成加锁 / 队列 / 409。

把 langgraph dev 直接上生产

你会看到无鉴权、无持久化、无扩容。因为dev 是本地开发模式。改成用 langgraph up 或自建 FastAPI + Postgres。

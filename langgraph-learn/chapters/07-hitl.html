07 · interrupt 与 HITL：让人在图中途接管

模型可以提议，但不能替人签字。LangGraph 的 interrupt() 把执行停在 checkpoint 上，等人给答案后从暂停点继续；这不是抛异常，也不是重新跑一遍。

读完你能做到

  • 在节点里调用 interrupt()，让图停在待确认状态
  • 用 Command(resume=...) 把用户答案送回暂停点
  • 说清「同一节点重入」与「从上一个 checkpoint 重跑」的区别
  • 处理多个中断，并给前端一个稳定的待确认契约

先说为什么：模型不能替人签字

删除文件、发邮件、下单、改生产配置，这些动作需要人确认。 如果在 Python 里 input()，图就阻塞在进程里，无法持久化、无法多副本、无法恢复。 interrupt 把「等人」变成图的一等状态。

最小可跑：一次暂停与恢复

from typing import TypedDict

from langgraph.checkpoint.memory import InMemorySaver
from langgraph.graph import END, START, StateGraph
from langgraph.types import Command, interrupt


class State(TypedDict):
    action: str
    approved: bool


def ask(state: State) -> dict:
    answer = interrupt({"question": f"是否执行 {state['action']}？"})
    return {"approved": bool(answer)}


def act(state: State) -> dict:
    return {"action": state["action"] + (" 已执行" if state["approved"] else " 已取消")}


builder = StateGraph(State)
builder.add_node("ask", ask)
builder.add_node("act", act)
builder.add_edge(START, "ask")
builder.add_edge("ask", "act")
builder.add_edge("act", END)

graph = builder.compile(checkpointer=InMemorySaver())
config = {"configurable": {"thread_id": "hitl-1"}}

graph.invoke({"action": "删除 /tmp/a.txt", "approved": False}, config)
# 此时图停在 ask，等待 resume
graph.invoke(Command(resume=True), config)
print(graph.get_state(config).values)

interrupt types.py:913 在节点内部调用，第一次执行到它会保存 checkpoint 并返回一个中断信号； 恢复时同一个节点会重新进入，这次 interrupt() 直接返回 resume 的值。

interrupt 的语义：不是抛异常

你以为实际
抛异常，节点中断保存 checkpoint，整个图暂停
恢复时从头跑从暂停节点重新进入，之前的副作用不重放
不需要 checkpointer没有 checkpointer 就无法恢复
resume 值只给当前节点值按中断 id 匹配，多个中断要分别恢复

GraphInterrupt errors.py:104 是内部冒泡机制，普通业务代码不应该捕获它当作失败。

Command(resume=...)：怎么把答案送回去

恢复时调用 graph.invoke(Command(resume=value), config)， config 必须还是同一个 thread_id。 值可以是布尔、字符串、字典；复杂表单建议用带 schema 的 dict。 

answer = {"approved": True, "reason": "已确认是测试文件"}
graph.invoke(Command(resume=answer), config)

多个中断与前端契约

一个 superstep 里可能有多个节点同时 interrupt。恢复时， Command(resume=...) 会按中断 id 匹配；如果只恢复一个，其他仍挂起。 前端至少要保存三样东西：thread_id、中断 id、待确认的 payload。

把「待确认」做成事件

流式模式下，中断会以事件形式出现；前端据此渲染确认框，用户提交后用同一个 thread_id 调 resume。不要把确认状态只放在浏览器内存里。

陷阱与窍门

在 interrupt 前做了副作用

你会看到恢复后重复发邮件 / 重复扣款。因为节点会重新进入，interrupt 之前的代码会再跑。改成把副作用放到 interrupt 之后，或用幂等键。

恢复时换了 thread_id

你会看到找不到暂停点，图从头开始。因为中断是按 thread 保存的。改成恢复时使用同一个 config。

没有 checkpointer 就调用 interrupt

你会看到恢复时报缺少 checkpointer。因为暂停状态无处持久化。改成编译时挂 checkpointer=...。

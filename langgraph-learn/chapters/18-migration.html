18 · 迁移与选型：LangGraph 与其他 Agent 框架

学到这里，你可能会问：我已经有 LangChain agent、AgentScope 或 Spring AI， 还要不要 LangGraph？这一章不做「谁更好」的结论，而是给出边界与迁移清单。

读完你能做到

  • 说清 LangGraph 负责哪一层：运行时、状态、持久化、interrupt
  • 比较 LangGraph、LangChain agents、AgentScope、Spring AI 的适用边界
  • 知道 0.x 到 1.x 的主要破坏性变化
  • 按项目情况做选型与迁移决定

先理解：LangGraph 到底负责哪一层

1.2.20 的仓库方向说明写得很明确：LangGraph 是低层运行时， 负责图执行、checkpoint、流式与 interrupt/resume； 更上层的 Agent 开发属于 harness（例如 Deep Agents）。 预构建的 create_react_agent 是维护模式，不再加新 Agent 能力。

对照：四种常见选择

选择强项适合
LangGraph状态、持久化、interrupt、可恢复执行需要精确控制流程与恢复
LangChain agents上手快、生态全简单工具循环、原型
AgentScope多智能体、服务化、Java/Python 双栈团队协作与服务托管
Spring AISpring 生态、Advisor、RAG已有 Spring 服务

它们不是互斥的：LangGraph 可以调用 LangChain 模型与工具； AgentScope / Spring AI 也可以用各自的编排层。选型的核心是「你的流程是否需要显式状态与恢复」。

从 0.x 到 1.x 的变化

  • 包版本：本站对齐 1.2.20 pyproject.toml:7； 0.2/0.3 的不少导入路径与参数已经变化。
  • create_react_agent 仍在，但定位为兼容 / 维护；新 Agent 建议显式搭图或上层 harness。
  • checkpoint / store 的包名与后端接口有调整；先看 langgraph-checkpoint 的版本约束。
  • 流式事件版本与 stream_mode 取值有扩展；旧教程的 stream_mode="values" 仍然可用，但事件形状要重新核对。
  • interrupt / resume 的语义更严格：没有 checkpointer 就不能恢复。

选型与迁移检查清单

问题为什么重要
流程是否需要中途暂停 / 人工确认？需要就选带 checkpoint + interrupt 的运行时
是否需要跨进程恢复？需要就排除纯内存方案
状态是否复杂到需要 reducer？复杂状态用图比手写 dict 更可控
是否已有 Spring / AgentScope 服务？已有生态可能比换框架更省事
是否只是简单工具循环？LangChain agent 或一个函数可能更简单
是否需要多 Agent 协作？先确认是职责隔离还是并行加速

再深入一点：实现细节与边界

四种方案的边界

方案状态 / 恢复适合
普通函数无一次性线性流程
LangChain agent弱简单工具循环
LangGraph强需要暂停、恢复、时间旅行
AgentScope / Spring AI框架自带服务层已有对应生态

0.x 到 1.x 的迁移顺序

  1. 先升包版本，跑最小图，确认导入路径。
  2. 再核对 checkpointer / store 的包与接口。
  3. 然后核对流式事件形状与 stream_mode。
  4. 最后处理 prebuilt 定位与 Agent 层的替代方案。

不要为了图而图

如果流程没有暂停、恢复、审计或多人协作需求，一个函数或 LangChain chain 更便宜。 LangGraph 的价值在运行时语义，不在「看起来更架构」。

陷阱与窍门

照抄 0.x 教程

你会看到导入失败或参数不存在。因为1.x 有破坏性变化。改成先核对本站版本与源码签名，再迁移。

为了「用 LangGraph」而用

你会看到简单流程被拆得很复杂。因为图的成本在状态与持久化。改成先问「我是否需要恢复与暂停」。

把 prebuilt 当长期架构

你会看到需求一复杂就要重写。因为它是维护模式。改成原型可以用，生产前评估显式图或 harness。

04 · Command、Send 与并行：动态路由和 map-reduce

条件边只能「选一条边」，不能同时改状态；当节点需要既更新 state 又指定下一个节点， 或者一条输入要分给 N 个节点并行处理时，就要用 Command 与 Send。

读完你能做到

  • 用 Command(update=..., goto=...) 在一个节点里同时改状态与跳转
  • 用 Send 做动态 fan-out，把一条输入分给多个节点
  • 理解并行节点的合并顺序与 reducer 的关系
  • 判断什么时候用 Send，什么时候普通边就够了

先说为什么：静态边不够用的时候

条件边是「先算路由，再走边」，路由函数只能返回路径，不能改 state。 如果你的节点已经知道「下一步是谁」，并且要顺手写一个字段，Command 更直接。 Send 解决另一类问题：运行时才知道要分几路，比如按文档列表逐篇总结。

最小可跑：Command 改写路由

from typing import TypedDict

from langgraph.graph import END, START, StateGraph
from langgraph.types import Command


class State(TypedDict):
    question: str
    route: str
    answer: str


def triage(state: State) -> Command:
    route = "billing" if "退款" in state["question"] else "general"
    return Command(update={"route": route}, goto=route)


def billing(state: State) -> dict:
    return {"answer": "进入退款流程"}


def general(state: State) -> dict:
    return {"answer": "进入通用回答"}


builder = StateGraph(State)
builder.add_node("triage", triage)
builder.add_node("billing", billing)
builder.add_node("general", general)
builder.add_edge(START, "triage")
builder.add_edge("billing", END)
builder.add_edge("general", END)

graph = builder.compile()
print(graph.invoke({"question": "我要退款", "route": "", "answer": ""}))

Command types.py:843 的 update 和 goto 会在同一个 superstep 里生效； 不需要再给 triage 加条件边。

Send：把一条输入分给 N 个节点

Send types.py:748 不是「一条边」，而是一组动态任务：路由函数返回 [Send("worker", {...}), ...]， 执行器会为每个 Send 启动一个实例。每个实例拿到的是自己那份输入，不是全局 state。 

from typing import Annotated, TypedDict
from operator import add

from langgraph.graph import END, START, StateGraph
from langgraph.types import Send


class State(TypedDict):
    docs: list[str]
    summaries: Annotated[list[str], add]
    report: str


def fan_out(state: State):
    return [Send("summarize", {"doc": d}) for d in state["docs"]]


def summarize(payload: dict) -> dict:
    return {"summaries": [payload["doc"][:20]]}


def merge(state: State) -> dict:
    return {"report": "\n".join(sorted(state["summaries"]))}


builder = StateGraph(State)
builder.add_node("summarize", summarize)
builder.add_node("merge", merge)
builder.add_conditional_edges(START, fan_out, ["summarize"])
builder.add_edge("summarize", "merge")
builder.add_edge("merge", END)

graph = builder.compile()
print(graph.invoke({"docs": ["a" * 30, "b" * 30], "summaries": []}))

这里 summaries 必须用 add 这类 reducer 合并， 否则多个并行实例写同一个字段会冲突。合并顺序不保证与输入顺序一致； 需要稳定顺序就在结果里带序号，最后统一排序。

并行结果的合并与顺序

字段类型并行写入的行为建议
无 reducer多个实例写同一字段会报 InvalidUpdateError每个实例写不同字段，或用 reducer
add / 自定义 reducer按 reducer 合并，顺序不保证结果里带序号，最后排序
消息列表add_messages 按 id 去重追加并行节点各写独立消息 id
Send 的输入不是全局 state

Send 的 payload 会作为该实例的初始输入。它看不到父图当前的全部字段， 需要什么就显式塞进 payload；这也是控制并行实例输入面的好机会。

工程实践：三种写法与排查

Command 与条件边怎么选

def triage(state: State) -> Command:
    return Command(update={"route": "billing"}, goto="billing")
def route(state: State) -> str:
    return state["route"]

builder.add_conditional_edges("triage", route, ["billing", "general"])
需求选择
同时改 state 与跳转Command
只根据 state 选边条件边
运行时才知道几路Send
固定两路并行普通边 + 两个节点

Send 的排查

  • payload 不是全局 state；缺少字段就在 fan-out 时补。
  • 汇总字段必须有 reducer，否则并行写会冲突。
  • 结果顺序不保证；需要稳定顺序就带 index 后排序。

再深入一点：实现细节与边界

Send 的 payload 设计

Send 的 payload 会成为该实例的初始输入。把「这一路需要的全部信息」显式放进去， 不要让子任务再去读全局 state；这既是隔离，也是可测试性。 

def fan_out(state: State):
    return [
        Send("summarize", {"doc": doc, "index": i})
        for i, doc in enumerate(state["docs"])
    ]


def summarize(payload: dict) -> dict:
    return {"summaries": [f'{payload["index"]}:{payload["doc"][:20]}']}

并行节点与 reducer

写法结果
两个节点写同一字段，无 reducerInvalidUpdateError
两个节点写同一字段，有 add按 reducer 合并
两个节点写不同字段都能保留

Command 与条件的取舍

需要「同一步既改 state 又跳转」用 Command； 只需要「根据 state 选边」用条件边。不要在 Command 里做重 IO， 它仍然是一个节点，失败会按节点重试 / 异常处理。

陷阱与窍门

Command 里 goto 到不存在的节点

你会看到运行时找不到目标节点。因为goto 必须是已注册节点名或 END。改成先注册节点，再拼 goto。

Send 的返回值和状态字段同名冲突

你会看到并行实例互相覆盖。因为字段没有 reducer。改成给汇总字段加 reducer，或让每个实例写独立 key。

用 Send 做固定两路并行

你会看到代码比普通边更复杂。因为Send 是为「运行时才知道几路」设计的。改成固定分支用普通边 + 多个节点即可。

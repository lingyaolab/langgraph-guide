22 · 安全与多租户：thread、Store 与工具边界

多租户不是「加个 user_id」。同一个 checkpointer、同一个 Store、同一套工具， 任何一处漏了隔离，都会让用户看到别人的数据。这一章按数据面逐层检查。

读完你能做到

  • 用 thread_id + 租户前缀隔离会话
  • 给 Store 的 namespace 加租户边界
  • 在工具层做权限检查，而不是只靠提示词
  • 知道 checkpoint / 日志里哪些数据不能落盘

先说为什么：模型不会替你守边界

「不要查别人的订单」写在提示词里，模型仍可能被诱导。 真正的隔离必须在代码层：查询条件带租户、工具检查身份、 Store 的 key 带租户、checkpoint 不跨 thread 读。

最小可跑：带租户的上下文

from dataclasses import dataclass

from langgraph.runtime import Runtime


@dataclass
class Context:
    user_id: str
    tenant_id: str


def load_orders(state: dict, runtime: Runtime[Context]) -> dict:
    ctx = runtime.context
    rows = db.query(
        "select * from orders where tenant_id = ? and user_id = ?",
        (ctx.tenant_id, ctx.user_id),
    )
    return {"orders": rows}

身份来自 Runtime Context，不来自模型参数。SQL 条件必须同时带租户与用户， 不能只带其中一个。

thread 隔离

数据隔离键漏了会怎样
checkpoint / 对话历史thread_id + 租户读到别人的会话
Store 偏好("tenants", tenant_id, "users", user_id)偏好串号
文件 / 工作区agent_id + 租户文件越权
日志 / trace租户字段 + 脱敏隐私泄漏

工具权限

工具的第一行应该是权限检查：这个用户能不能查这个订单、能不能写这个文件。 检查失败返回可读错误，而不是抛异常或让模型自己判断。 

def query_order(order_no: str, runtime: Runtime[Context]) -> str:
    ctx = runtime.context
    order = db.find(order_no)
    if order is None or order.tenant_id != ctx.tenant_id:
        return "订单不存在或无权限"
    return order.status

工程实践：三种写法与排查

三处必须带租户

config = {"configurable": {"thread_id": f"{tenant}:{user}:{sid}"}}
store.put(("tenants", tenant, "users", user), "pref", {...})
db.query("... where tenant_id = ? and user_id = ?", (tenant, user))
现象原因改法
知道 id 就能读别人会话没校验 thread 归属读取前鉴权
偏好串号namespace 少了租户tenant 放第一段
工具查越权订单只靠提示词工具内检查归属
trace 泄漏隐私记录完整 prompt脱敏 / 采样

再深入一点：实现细节与边界

checkpoint 的读取也要鉴权

知道 thread_id 不等于有权限。读 get_state / get_state_history 前，先校验该 thread 属于当前租户与用户。

工具的三层检查

层检查什么
路由层这个用户能否访问这个 Agent / thread
工具层能否查这条订单、写这个文件
数据层SQL / API 是否强制带租户条件

日志与 trace

  • 默认不记录完整 prompt / completion；需要时脱敏。
  • trace 里不要出现密钥、完整手机号、身份证。
  • 按租户分桶查询，避免跨租户排障时看到别人数据。

陷阱与窍门

thread_id 只做随机数

你会看到知道 id 就能读别人会话。因为没有校验归属。改成读 checkpoint 前先校验 thread 属于当前租户。

Store 的 key 只用 user_id

你会看到不同租户的同名用户互相覆盖。因为namespace 少了 tenant。改成所有 key 从租户开始。

把密钥写进 state / 日志

你会看到checkpoint 或 trace 里出现明文 key。因为state 会持久化。改成只放引用，运行时从密钥服务取。

20 分钟动手练习

  1. 用两个租户的 thread_id 交错调用，确认读不到对方历史。
  2. 把 Store 的 namespace 从 user_id 改成 tenant + user，验证隔离。
  3. 写一个工具，检查订单归属，越权时返回可读错误。

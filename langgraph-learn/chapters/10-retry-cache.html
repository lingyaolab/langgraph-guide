10 · 重试、缓存与节点控制：失败路径也是图的一部分

生产图一定会遇到限流、超时、网络抖动。重试与缓存不是「加个装饰器」， 它们会改变状态、成本与幂等性。这一章把策略放在节点级别讲清。

读完你能做到

  • 给节点配置 RetryPolicy，只重试值得重试的错误
  • 用 CachePolicy 缓存纯函数节点，避免重复计算
  • 设置递归上限与超时，区分「业务失败」与「框架兜底」
  • 判断哪些节点绝对不能重试

先说为什么：失败不是异常，是状态

一次工具调用失败，可能应该重试，也可能应该把错误写回消息让模型换方案。 在图里，失败会变成节点结果或异常冒泡；重试策略决定它走哪条路。 不区分可重试与不可重试，会把 401 也重试十次，延迟和账单一起爆炸。

最小可跑：给节点加重试

from langgraph.graph import END, START, StateGraph
from langgraph.types import RetryPolicy


def flaky(state: dict) -> dict:
    # 真实场景：网络请求 / 模型调用
    return {"ok": True}


builder = StateGraph(dict)
builder.add_node(
    "flaky",
    flaky,
    retry_policy=RetryPolicy(
        max_attempts=3,
        initial_interval=0.5,
        retry_on=RuntimeError,   # 演示用；生产改成你的可重试异常
    ),
)
builder.add_edge(START, "flaky")
builder.add_edge("flaky", END)
graph = builder.compile()

RetryPolicy types.py:428 的 max_attempts 包含首次尝试；具体异常是否重试由策略里的 retry_on 决定。默认不是「所有异常都重试」，演示里要显式写 retry_on=RuntimeError，生产里换成你的可重试异常。

缓存：什么能缓存，什么不能

CachePolicy types.py:531 按节点输入生成缓存键。它适合纯函数：同样的输入永远得到同样的输出。 带副作用、依赖当前时间、依赖用户身份的节点不要缓存。

节点类型能缓存？原因
纯文本转换、格式化是输入决定输出
检索（同一索引版本）是可加索引版本到 key
模型调用谨慎温度、模型版本、上下文都会变
写数据库 / 发邮件否副作用不可重放
依赖当前时间否同样的输入不同时间结果不同

超时与递归上限

递归上限是执行器兜底：_loop.py _loop.py:1917 里 stop = step + recursion_limit + 1，超过就抛 GraphRecursionError errors.py:69。 它不能替代业务停止条件。

  • 节点内部超时：用 asyncio.timeout 或 HTTP 客户端超时。
  • 图级总时长：在外层用任务超时，取消整个执行。
  • 重试预算：重试次数 × 单次超时，不能超过用户能接受的总延迟。

陷阱与窍门

写操作节点重试

你会看到重复下单 / 重复扣款。因为第一次可能已经成功，只是响应超时。改成加幂等键，或把写操作设计成可检测的幂等。

把 401 也重试

你会看到延迟翻倍但永远不会成功。因为鉴权错误不可重试。改成只对 429 / 5xx / 网络错误重试。

缓存了带用户身份的节点

你会看到用户 A 看到用户 B 的结果。因为缓存键没有包含身份。改成把 tenant/user 放进 key，或不缓存。

自检三问

  2. 哪些节点绝对不能缓存？为什么？
  3. 递归上限与业务停止条件分别负责什么？

20 分钟动手练习

  1. 写一个前两次失败、第三次成功的节点，配 RetryPolicy 观察总耗时。
  2. 给一个纯函数节点加 CachePolicy，连续调用两次，确认第二次没有执行函数。
  3. 把递归上限调小，构造一个循环，记录 GraphRecursionError 的文本。

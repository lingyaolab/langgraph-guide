06 · 时间旅行与状态编辑：回放、分叉与人工修正

有了 checkpoint，图就不只有「当前状态」，还有一条历史。 你可以读任意一步、从旧点重跑、甚至直接改 state 再继续。这一章讲清这些操作的语义与风险。

读完你能做到

  • 用 get_state 读当前状态，用 get_state_history 读历史
  • 从某个历史 checkpoint 重跑，理解「回放」与「分叉」的区别
  • 用 update_state 人工修正状态，并知道它会不会触发节点
  • 说清时间旅行在调试、人工修正与 A/B 对比中的边界

先说为什么：调试不是重跑一遍

复现一个 bug 通常需要「当时的输入、当时的 state、当时走的那条边」。 重跑只能碰运气；checkpoint 把这些都留下来了。时间旅行让你从故障前一步继续， 而不是从头再烧一遍 token。

最小可跑：读一次历史并回放

config = {"configurable": {"thread_id": "demo"}}

# 当前状态
snapshot = graph.get_state(config)
print(snapshot.values)
print(snapshot.next)

# 历史，从新到旧
for item in graph.get_state_history(config):
    print(item.config["configurable"]["checkpoint_id"], item.metadata["step"])

get_state main.py:1460 返回当前快照；get_state_history main.py:1510 返回整条链。每个快照都带自己的 checkpoint_id 与 step。

update_state：改状态而不改代码

graph.update_state(
    config,
    {"messages": [("user", "这是一条人工补录的消息")]},
    as_node="agent",
)

update_state main.py:2613 会把这次修改写成一个新的 checkpoint。默认它像某个节点刚跑完一样合并 state； as_node 决定用哪个节点的写入语义。它不会自动继续执行，下一次 invoke 才继续。

update_state 不是「改历史」

它追加一个新的 checkpoint，旧历史还在。想在旧点分叉，要先拿到那个 checkpoint_id，再以它为父继续跑。

分叉：从旧 checkpoint 开新分支

history = list(graph.get_state_history(config))
old = history[-2]   # 选一个较早的点

fork_config = graph.update_state(
    old.config,
    {"messages": [("user", "换一个方向重试")]},
    as_node="agent",
)

graph.invoke(None, fork_config)   # 从分叉点继续

分叉的语义是「新的 checkpoint 以旧 checkpoint 为父」，原来的线程继续保留。 这适合 A/B 对比与「回滚到某一步再试」，但要注意外部副作用（发邮件、写数据库）不会自动回滚。

工程实践：三种写法与排查

历史、回放与分叉

# 读历史
history = list(graph.get_state_history(config))

# 改状态
graph.update_state(config, {"note": "人工修正"}, as_node="agent")

# 从旧点分叉
fork = graph.update_state(history[-2].config, {"note": "换方案"}, as_node="agent")
graph.invoke(None, fork)
操作会不会重跑节点会不会回滚外部副作用
get_state不会不会
update_state不会，下一次 invoke 才继续不会
从旧 checkpoint 分叉会重跑分叉后的节点不会

排查顺序

  1. 先看历史里「第一次出现坏值」的快照。
  2. 再看它的 next，确认当时准备执行哪个节点。
  3. 最后从它的前一步回放，复现问题。

再深入一点：实现细节与边界

回放与分叉的区别

操作结果适合
从旧 checkpoint 继续产生新的分叉链A/B 对比、回滚重试
update_state 后继续人工修正后重跑补数据、改判断
重新 invoke从当前线程最新状态继续正常多轮

分叉后的外部副作用

checkpoint 只保存图内状态。发邮件、写数据库、调用第三方 API 不会回滚。 要支持安全重放，外部操作必须有幂等键，或在分叉前记录已执行的操作 id。 

fork = graph.update_state(
    old.config,
    {"messages": [("user", "换一个方案")]},
    as_node="agent",
)
graph.invoke(None, fork)

调试时间线的顺序

  1. get_state_history 从新到旧列出快照。
  2. 找到故障前最后一个 next 非空的快照。
  3. 从它的 config 回放，或在它上面 update_state。

陷阱与窍门

把时间旅行当成事务回滚

你会看到外部系统已经产生了重复副作用。因为checkpoint 只回滚图内状态。改成把副作用做成幂等，或记录外部操作 id。

用 update_state 改完就以为节点会重跑

你会看到状态变了但流程没继续。因为update_state 只写 checkpoint。改成再调一次 invoke(None, config)。

分叉后还用原 thread_id 查当前状态

你会看到读到的不是分叉分支。因为分叉有新的 checkpoint 链。改成保存分叉返回的 config，用它继续。

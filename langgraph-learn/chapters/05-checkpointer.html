05 · Checkpointer 与 thread_id：断点、恢复与多轮

默认情况下，图跑完就忘。要让多轮对话、失败恢复、人工暂停成立， 必须给图挂一个 checkpointer，并用 thread_id 把同一条会话串起来。

读完你能做到

  • 给图挂 InMemorySaver，用同一个 thread_id 跑两轮
  • 说清 checkpoint 在什么时机写入、里面存了什么
  • 在 SQLite / Postgres 之间选一个后端，并知道初始化步骤
  • 解释为什么换一个 thread_id 就等于开新会话

先说为什么：图默认不记得上一次

图是「一次执行」的编排，不是会话容器。没有 checkpointer 时， 每次 invoke 都从你给的输入重新开始；上一轮的 messages 不会自动带过来。 多轮对话不是模型记住了，而是你把历史从 checkpoint 里读出来再喂回去。

最小可跑：两轮对话共享 thread_id

from langgraph.checkpoint.memory import InMemorySaver
from langgraph.graph import END, START, MessagesState, StateGraph


def echo(state: MessagesState) -> dict:
    last = state["messages"][-1]
    return {"messages": [("ai", f"你说了：{last.content}")]}


builder = StateGraph(MessagesState)
builder.add_node("echo", echo)
builder.add_edge(START, "echo")
builder.add_edge("echo", END)

graph = builder.compile(checkpointer=InMemorySaver())

config = {"configurable": {"thread_id": "user-1"}}
graph.invoke({"messages": [("user", "我叫 Alice")]}, config)
out = graph.invoke({"messages": [("user", "我叫什么？")]}, config)
print(out["messages"][-1].content)

同一个 thread_id 下，第二次 invoke 会先加载上一次的 checkpoint， 再把新消息合并进 messages。换成 user-2，历史就是空的。

Checkpoint 里到底存了什么

checkpointer 的契约在 BaseCheckpointSaver base/__init__.py:199， 核心是 get_tuple / put / list。 执行器在每个 superstep 之后写一次： _loop.py:768。

内容用途
channel_values当前 state 的各个字段
channel_versions每个字段的版本，用于冲突检测与增量
versions_seen哪些节点已经看过哪个版本
pending_writes已产生但还没合并的写入
metadatastep、source、run_id 等

这也解释了为什么 state 里的字段必须可序列化：checkpoint 要把它写进内存 / SQLite / Postgres。

后端选型：内存、SQLite、Postgres

后端适合注意
InMemorySavermemory/__init__.py:34单元测试、单进程演示进程退出即丢
SqliteSaversqlite/__init__.py:49本地持久化、单机服务要先 setup() 建表
PostgresSaverpostgres/__init__.py:45多副本、生产要先 setup()，连接池要配
 
import sqlite3

from langgraph.checkpoint.sqlite import SqliteSaver

conn = sqlite3.connect("checkpoints.db", check_same_thread=False)
checkpointer = SqliteSaver(conn)
checkpointer.setup()

graph = builder.compile(checkpointer=checkpointer)

再深入一点：实现细节与边界

SQLite 的线程参数

SQLite 连接默认不允许跨线程使用。LangGraph 的异步执行可能在不同线程里访问连接， 所以本地示例要传 check_same_thread=False，并自己保证串行写入。 

import sqlite3
from langgraph.checkpoint.sqlite import SqliteSaver

conn = sqlite3.connect("checkpoints.db", check_same_thread=False)
saver = SqliteSaver(conn)
saver.setup()

看当前停在哪

snapshot = graph.get_state(config)
print(snapshot.values)   # 当前 state
print(snapshot.next)     # 下一步要执行的节点（空 tuple 表示结束）
print(snapshot.config)   # 这个快照的 config，可用于回放

什么时候会写 checkpoint

  • 每个 superstep 结束；不是每个节点结束都写，并行节点会合批。
  • 输入节点、恢复、update_state、fork 也会写。
  • state 越大，写入越慢；不要把文件内容直接塞进 state。

陷阱与窍门

调用时忘了传 config

你会看到每次都是新会话，历史不增长。因为没有 thread_id 就找不到对应 checkpoint。改成所有调用都传同一个 {"configurable": {"thread_id": ...}}。

以为 InMemorySaver 能跨进程

你会看到重启后历史全丢。因为它只存在当前进程内存。改成本地用 SQLite，多副本用 Postgres。

把大对象塞进 state

你会看到checkpoint 体积暴涨、写入变慢。因为每个 superstep 都会写一次。改成state 只放必要字段，大文件走外部存储。

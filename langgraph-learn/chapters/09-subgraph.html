09 · 子图与模块化：把一张图装进另一张图

一张图超过十几个节点后，调试和复用都会变难。子图让你把一组节点封装成「一个节点」， 父图只关心它的输入输出，不关心内部怎么走。

读完你能做到

  • 把编译后的子图直接当节点加进父图
  • 在父图与子图之间共享 state，或做字段映射
  • 从流式事件的命名空间看出「现在在哪个子图里」
  • 判断什么时候该拆子图，什么时候只是多写了几个节点

先说为什么：一张图不该无限长

子图的价值不是「看起来模块化」，而是三件事：复用同一段流程、隔离状态 schema、 在流式与调试里形成清晰的命名空间。没有这三件事，拆子图只会增加跳转成本。

最小可跑：父图调用子图

from typing import TypedDict

from langgraph.graph import END, START, StateGraph


class SubState(TypedDict):
    text: str


def upper(state: SubState) -> dict:
    return {"text": state["text"].upper()}


sub = StateGraph(SubState)
sub.add_node("upper", upper)
sub.add_edge(START, "upper")
sub.add_edge("upper", END)
sub_graph = sub.compile()


class ParentState(TypedDict):
    text: str


parent = StateGraph(ParentState)
parent.add_node("normalize", lambda s: {"text": s["text"].strip()})
parent.add_node("upper", sub_graph)   # 编译后的图就是一个节点
parent.add_edge(START, "normalize")
parent.add_edge("normalize", "upper")
parent.add_edge("upper", END)

print(parent.compile().invoke({"text": "  hello  "}))

子图不需要额外的包装器；编译后的图本身就是可调用节点。 父图只要求子图的输入 / 输出能与父图 state 对上。

状态怎么传：共享、映射与隔离

方式行为适合
共享同一个 State父子图读写同一组字段流程强相关、字段少
子图独立 schema父图只传子图声明的字段复用、隔离内部状态
显式映射函数在节点里把父 state 转成子 state，再把结果转回字段名或结构不同

如果父子图字段同名但语义不同，优先用显式映射，而不是硬共享。 子图的内部字段不应该污染父图的 checkpoint。

命名空间与调试

子图执行时，事件会带命名空间（例如 parent:sub）。 流式事件、checkpoint 与错误栈都会带上它；看到命名空间就知道问题在父图还是子图。 子图内部也可以有自己的 checkpointer，但通常由父图统一管理。

先拆「可复用」，再拆「看起来大」

一段流程被两个父图复用，或需要独立测试时，才拆子图。 只是为了减少文件长度，普通函数更轻。

陷阱与窍门

子图 schema 与父图不兼容

你会看到运行时缺少字段或类型错误。因为父图传进去的 dict 不满足子图 State。改成用映射函数补齐字段，或统一 schema。

父子图各挂一个 checkpointer

你会看到恢复点混乱。因为两层都在写自己的 checkpoint。改成通常只让父图挂，子图作为纯节点执行。

在子图里用全局变量传状态

你会看到并行或重放时结果不稳定。因为全局变量不进入 checkpoint。改成所有需要恢复的状态都放进 State。

自检三问

  1. 编译后的子图为什么可以直接当节点用？
  2. 父子图共享 schema 与独立 schema 各适合什么场景？
  3. 命名空间在调试里解决什么问题？

20 分钟动手练习

  1. 把 03 章的退款 / 通用路由拆成一个子图，父图只负责入口与退出。
  2. 给子图加一个父图没有的字段，观察父图最终 state 是否包含它。
  3. 用 stream_mode="updates" 跑父子图，记录事件里的命名空间。

27 · 案例五：生产部署

本地能跑不代表能上线。这个案例把前面的图接到 Postgres、SSE、多租户与健康检查上， 给出一个最小但完整的生产骨架。

读完你能做到

  • 用 langgraph.json 暴露图，并区分 dev / up
  • 把 checkpointer 与 store 换成 Postgres
  • 用 FastAPI + SSE 包装图，处理取消与断线
  • 按 thread / tenant 隔离，并给上线验收清单

先说为什么：图和进程要分开

图是逻辑，进程是运行环境。生产化的核心是让 checkpoint、store、并发与部署形态解耦， 而不是把 invoke 包一层 HTTP 就完事。

案例：一条生产请求

HTTP /chat
  → 鉴权，得到 tenant / user / thread
  → 同一 thread 串行
  → graph.astream(..., stream_mode="messages")
  → SSE token / citations / done
  → checkpoint 落 Postgres

FastAPI + SSE

from fastapi import FastAPI
from fastapi.responses import StreamingResponse

app = FastAPI()


@app.post("/chat")
async def chat(body: ChatBody):
    config = {
        "configurable": {
            "thread_id": f'{body.tenant}:{body.user}:{body.thread}',
            "user_id": body.user,
        }
    }

    async def events():
        async for message, meta in graph.astream(
            {"messages": [("user", body.question)]},
            config,
            stream_mode="messages",
        ):
            text = message.content
            if text:
                yield f"data: {json.dumps({'type': 'token', 'text': text})}\n\n"
        yield f"data: {json.dumps({'type': 'done'})}\n\n"

    return StreamingResponse(events(), media_type="text/event-stream")

多租户与串行

问题做法
会话隔离thread_id 带 tenant + user
偏好隔离Store namespace 从 tenant 开始
同 thread 并发锁 / 队列 / 409
SSE 断线同 thread 重新订阅，不重新提交

上线验收

  1. readiness 检查 Postgres 与 checkpoint 表。
  2. 同一 thread 重复提交只执行一次。
  3. SSE 有心跳，反代关闭缓冲。
  4. 日志与 trace 脱敏，不出现密钥。
  5. 回滚方案：上一版镜像 + 数据库迁移脚本。

陷阱与窍门

多副本用 InMemorySaver

你会看到请求落到不同副本时历史丢失。因为checkpoint 只在单进程。改成Postgres。

SSE 被 Nginx 缓冲

你会看到前端一次性收到全部内容。因为代理开了 buffering。改成关闭缓冲 + 心跳。

重复提交同一 thread

你会看到状态互相覆盖。因为没有串行。改成锁 / 队列 / 409。

自检三问

  1. 生产环境为什么不能用 InMemorySaver？
  2. SSE 断线后应该重新提交还是重新订阅？
  3. 上线验收至少要看哪三类状态？

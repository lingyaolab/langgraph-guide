02 · State、Schema 与 Reducer：状态不是一个大字典

图里最容易被低估的是「状态怎么更新」。同一个字段，默认是覆盖、追加还是自定义合并， 决定了并行节点会不会互相踩、消息会不会丢。这一章把语义写进类型。

读完你能做到

  • 用 TypedDict / dataclass / Pydantic 定义 State，并知道何时选哪种
  • 用 Annotated[..., reducer] 声明字段的合并方式
  • 说清默认覆盖、add_messages 追加、以及自定义 reducer 的差异
  • 看懂 InvalidUpdateError 与「并行节点写同一字段」的关系

先说为什么：状态更新的语义要写进类型

如果状态只是一个普通 dict，你永远不知道某个字段是「覆盖」还是「追加」； 两个并行节点同时返回 {"items": [...]} 时，谁赢也没有定义。 LangGraph 把这件事变成 schema 的一部分：字段类型上写 reducer，执行器按它合并。

最小可跑：一个会累加的字段

from operator import add
from typing import Annotated, TypedDict

from langgraph.graph import END, START, StateGraph


class State(TypedDict):
    total: Annotated[int, add]


def add_one(state: State) -> dict:
    return {"total": 1}


builder = StateGraph(State)
builder.add_node("add_one", add_one)
builder.add_edge(START, "add_one")
builder.add_edge("add_one", END)
graph = builder.compile()

print(graph.invoke({"total": 0}))   # {'total': 1}

把 add 换掉，语义就变了；把 Annotated 去掉， 第二次执行会覆盖而不是累加。状态字段的「怎么合并」不是运行时选项，而是类型声明。

Schema 的三种写法与选择

写法适合注意
TypedDict大多数图状态轻量、无运行时校验
dataclass想要默认值与类型提示字段默认值要小心可变对象
Pydantic BaseModel需要运行时校验与 LangChain 消息混用时注意序列化

Reducer：覆盖、追加与自定义

默认行为是覆盖：节点返回什么，字段就变成什么。 声明 Annotated[T, reducer] 后，旧值与新值会交给 reducer 合并。 消息字段用框架提供的 add_messages message.py:64， 它会按消息 id 去重、追加并处理 RemoveMessage。 

from langgraph.graph import MessagesState


class State(MessagesState):
    # 额外字段照常声明
    user_id: str

MessagesState message.py:310 只是预置了 messages: Annotated[list, add_messages] 的 TypedDict； 你仍然可以继承它加字段。

内置 channel语义典型用途
LastValuelast_value.py:20只保留最后一个值普通标量字段
Topictopic.py:23可累积的 pub-sub多路事件
BinaryOperatorAggregatebinop.py:66二元操作合并add、max

add_messages 到底做了什么

  • 把新消息追加到列表末尾。
  • 按消息 id 去重：同 id 的新消息会替换旧消息。
  • 识别 RemoveMessage，从列表里删掉指定 id。
  • 不负责裁剪长度；窗口裁减要自己写 reducer 或节点。

工程实践：三种写法与排查

三种 reducer 写法

class State(TypedDict):
    # 1. 默认覆盖
    status: str
    # 2. 追加
    logs: Annotated[list[str], operator.add]
    # 3. 自定义合并
    tags: Annotated[list[str], merge_tags]

消息去重与删除

from langchain_core.messages import RemoveMessage

def trim(state: MessagesState) -> dict:
    return {"messages": [RemoveMessage(id=m.id) for m in state["messages"][:-4]]}
现象原因改法
并行写同一字段报错没有 reducer加 Annotated
消息只剩最后一条字段不是 add_messages继承 MessagesState
消息重复新消息 id 与旧消息相同让每条消息有唯一 id
state 越来越大把大对象放进字段只存 id / 摘要

reducer 是图里最像「数据库 schema」的部分。先定字段语义，再写节点； 反过来的代码通常会在并行或恢复时出问题。

再深入一点：实现细节与边界

自定义 reducer

内置 reducer 不够时，写一个纯函数：参数是旧值与新值，返回合并后的值。 它可能被多次调用，所以不能有副作用。 

def merge_tags(left: list[str], right: list[str]) -> list[str]:
    return sorted(set(left) | set(right))


class State(TypedDict):
    tags: Annotated[list[str], merge_tags]

删除消息：RemoveMessage

add_messages 不只追加，也识别删除指令。 需要从历史里移除某条消息时，返回一个 RemoveMessage： 

from langchain_core.messages import RemoveMessage


def forget(state: MessagesState) -> dict:
    first = state["messages"][0]
    return {"messages": [RemoveMessage(id=first.id)]}

字段设计的三个建议

  • 能推导出来的值不要存：它会让 checkpoint 变大，还容易与源字段不一致。
  • 并行写入的字段一定加 reducer；顺序敏感的字段显式排序。
  • 大对象放外部存储，state 里只放 id 或摘要。

陷阱与窍门

并行节点写同一个非 reducer 字段

你会看到 InvalidUpdateErrorerrors.py:92。因为同一 superstep 里两个节点都更新了 LastValue，执行器不知道谁赢。改成给字段加 reducer，或让两个节点写不同字段。

把消息列表当普通 list

你会看到历史消息被覆盖，只剩最后一条。因为字段没有声明 add_messages。改成继承 MessagesState 或手写 Annotated[list, add_messages]。

reducer 有副作用

你会看到重放或并行时结果不稳定。因为reducer 可能被多次调用。改成保持纯函数，不要在里面写数据库。

13 · 记忆：短期状态、长期 Store 与跨会话

checkpointer 记住「这条会话发生过什么」，Store 记住「这个用户是谁」。 两者解决不同问题，混用会导致上下文膨胀或偏好丢失。这一章把边界讲清。

读完你能做到

  • 说清短期记忆（State + checkpointer）与长期记忆（Store）的分工
  • 用 BaseStore 的 namespace / key 存一个用户偏好
  • 在 InMemoryStore 与 PostgresStore 之间选型
  • 让同一个用户的不同 thread 共享偏好，但不共享对话历史

先说为什么：短期靠 state，长期靠 store

把用户偏好塞进 messages，它会随着对话增长被压缩、被裁掉； 把整段对话塞进 Store，它会无限膨胀且难以检索。 正确的分工是：对话历史留在 State，跨会话事实放 Store。

最小可跑：记住用户偏好

from langgraph.graph import END, START, MessagesState, StateGraph
from langgraph.store.memory import InMemoryStore


store = InMemoryStore()


def remember(state: MessagesState, config, store) -> dict:
    user_id = config["configurable"]["user_id"]
    store.put(("users", user_id), "preference", {"tone": "concise"})
    return {"messages": [("ai", "记住了：回答尽量简洁。")]}


def recall(state: MessagesState, config, store) -> dict:
    user_id = config["configurable"]["user_id"]
    item = store.get(("users", user_id), "preference")
    tone = item.value["tone"] if item else "default"
    return {"messages": [("ai", f"当前语气：{tone}")]}


builder = StateGraph(MessagesState)
builder.add_node("remember", remember)
builder.add_node("recall", recall)
builder.add_edge(START, "remember")
builder.add_edge("remember", "recall")
builder.add_edge("recall", END)

graph = builder.compile(store=store)
config = {"configurable": {"thread_id": "t-1", "user_id": "alice"}}
graph.invoke({"messages": [("user", "以后回答简洁点")]}, config)

config2 = {"configurable": {"thread_id": "t-2", "user_id": "alice"}}
print(graph.invoke({"messages": [("user", "我的语气偏好？")]}, config2))

BaseStore base/__init__.py:708 的 put / get / search 都以 namespace 元组为第一参数。 同一个用户的两个 thread 共享 ("users", "alice")，但各自的 messages 仍在自己的 checkpoint 里。

短期记忆：messages 与摘要

短期记忆的最小实现就是 MessagesState + checkpointer。 对话变长后，需要压缩：保留最近 N 条，或把旧消息摘要成一条系统消息。 压缩是业务策略，不是 checkpointer 自动做的。

策略做法代价
窗口只保留最近 N 条丢早期细节
摘要用模型把旧消息压缩成一段多一次模型调用
检索把历史存 Store，按需检索多一层索引与延迟

长期记忆：namespace、key 与检索

namespace 是逻辑分区，key 是条目名。常见设计： ("users", user_id) 存偏好，("facts", tenant_id) 存团队事实。 search base/__init__.py:784 支持按 namespace 前缀与过滤条件查，适合「找出所有相关偏好」。

后端适合注意
InMemoryStorememory/__init__.py:136单进程 / 测试进程退出即丢
PostgresStorebase.py:668多副本 / 生产要建表，连接池要配

陷阱与窍门

把对话历史写进 Store

你会看到Store 无限增长、检索变慢。因为历史应该是 thread 级短期状态。改成对话留 State，只把稳定事实写 Store。

Store 的 key 没带租户

你会看到用户 A 读到 B 的偏好。因为namespace 少了 tenant/user。改成所有 key 都带租户前缀。

以为 Store 会自动注入提示词

你会看到模型不知道偏好。因为Store 只是存储，不会自动拼上下文。改成在节点里检索并写进 messages。

  3. Store 的 namespace 设计为什么要带租户 / 用户？

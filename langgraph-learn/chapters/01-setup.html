01 · 环境与第一个图：StateGraph 从 0 跑通

LangGraph 不是「另一个模型 SDK」，它是一层状态机编排：你定义状态、节点和边， 它负责调度、合并与持久化。这一章先跑通一张最小的图，不接模型。

读完你能做到

  • 装好 Python 3.10+ 与 langgraph，跑通第一个 StateGraph
  • 说清 StateGraph、节点函数、compile() 三者各自负责什么
  • 知道 invoke 的输入是 state 的一部分，输出是合并后的 state
  • 能判断什么时候该用图、什么时候一个函数就够了

先说为什么：为什么不用一个大函数

一个函数也能做「取数据 → 调模型 → 存结果」。图的价值在三个地方： 每一步的状态可观察、可以中途暂停与恢复、可以把不同团队写的子流程拼起来。 如果这三件事你都不需要，普通函数更简单。

最小可跑：20 行的一张图

python -m venv .venv
# Windows: .venv\Scripts\activate
# macOS/Linux: source .venv/bin/activate
pip install "langgraph==1.2.20"
from typing import TypedDict

from langgraph.graph import END, START, StateGraph


class State(TypedDict):
    text: str


def upper(state: State) -> dict:
    return {"text": state["text"].upper()}


builder = StateGraph(State)
builder.add_node("upper", upper)
builder.add_edge(START, "upper")
builder.add_edge("upper", END)

graph = builder.compile()

print(graph.invoke({"text": "hello langgraph"}))

运行结果：{'text': 'HELLO LANGGRAPH'}。 这一张图没有模型、没有网络、没有 API Key，但它已经具备调度、状态合并与可持久化的全部骨架。

逐行解读：三个对象与两次编译

StateGraph(State) state.py:131 只负责「记下节点、边与状态 schema」，它本身不可执行。节点用 add_node state.py:376 注册，边用 add_edge state.py:928。 真正的执行器在 compile() state.py:1177 时才生成。

对象职责什么时候用
StateGraph建图：状态、节点、边启动时
节点函数读 state，返回要更新的字段每次执行到该节点
CompiledStateGraph调度、合并、持久化compile() 之后

节点返回的是 partial state，不是完整 state。你只返回想改的字段， 没返回的字段保持不变；这是后面所有 reducer 语义的起点。

端到端：invoke 到底做了什么

graph.invoke({"text": "hello"})
  → 校验输入（只允许 State 里声明的字段）
  → 从 START 找到第一条边
  → 执行 upper(state)
  → 把返回值合并进 state
  → 沿边走到 END
  → 返回最终 state

执行入口是 Pregel.invoke main.py:3870。 图对象可以重复调用，每次调用都是一次独立的执行；默认不保留上一次的状态。

陷阱与窍门

把 StateGraph 当函数直接调用

你会看到 TypeError: 'StateGraph' object is not callable。因为它还没编译。改成先 compile()，再 invoke。

节点返回了完整 state

你会看到未修改的字段被覆盖成旧值。因为返回的字典会按 reducer 合并。改成只返回要改的字段。

忘了连 END

你会看到图跑完一个节点后停住或报无出口。因为没有边告诉它下一步。改成给最后一条边加 END。

自检三问

  1. StateGraph 与 compile() 之后的对象，职责有什么不同？
  2. 节点为什么只返回 partial state？如果返回完整 state 会怎样？
  3. 什么情况下不该用图，而应该用一个普通函数？

  3. 故意删掉 add_edge("upper", END)，把报错原文记下来。

25 · 案例三：工单审批流

需求：客服可以创建退款工单，但创建前必须人工确认；确认后不能重复创建。 这个案例把 interrupt、checkpoint、幂等键与恢复接起来。

读完你能做到

  • 在节点里用 interrupt 暂停，等待人工确认
  • 用同一个 thread_id + Command(resume=...) 恢复
  • 用幂等键保证重复恢复不会重复创建工单
  • 处理拒绝、超时与重复提交

先说为什么：写操作不能靠模型自觉

「创建工单」有副作用。模型可能误判、用户可能反悔、网络可能超时重试。 暂停让人确认，checkpoint 让暂停可恢复，幂等键让重试安全。

案例：一次审批

用户：帮我退款
→ draft（生成工单草稿）
→ approval（interrupt，等人）
→ create（幂等创建）
→ notify（通知）

装配：审批与幂等

from typing import TypedDict

from langgraph.checkpoint.memory import InMemorySaver
from langgraph.graph import END, START, StateGraph
from langgraph.types import Command, interrupt


class State(TypedDict):
    order_id: str
    reason: str
    approved: bool
    ticket_id: str
    idempotency_key: str


def draft(state: State) -> dict:
    return {"idempotency_key": f'create-ticket:{state["order_id"]}'}


def approval(state: State) -> dict:
    ok = interrupt({
        "type": "approval",
        "title": "创建退款工单",
        "order_id": state["order_id"],
        "reason": state["reason"],
    })
    return {"approved": bool(ok)}


def create(state: State) -> dict:
    if not state["approved"]:
        return {"ticket_id": ""}
    # 真实场景：先按幂等键查，再创建
    existing = ticket_db.find_by_key(state["idempotency_key"])
    if existing:
        return {"ticket_id": existing.id}
    ticket = ticket_db.create(
        order_id=state["order_id"],
        reason=state["reason"],
        idempotency_key=state["idempotency_key"],
    )
    return {"ticket_id": ticket.id}


builder = StateGraph(State)
builder.add_node("draft", draft)
builder.add_node("approval", approval)
builder.add_node("create", create)
builder.add_edge(START, "draft")
builder.add_edge("draft", "approval")
builder.add_edge("approval", "create")
builder.add_edge("create", END)

graph = builder.compile(checkpointer=InMemorySaver())

恢复：同一个 thread，带答案

config = {"configurable": {"thread_id": "ticket-1"}}
graph.invoke({"order_id": "SO-1", "reason": "质量问题", "approved": False, "ticket_id": "", "idempotency_key": ""}, config)

# 人工确认后
graph.invoke(Command(resume=True), config)
print(graph.get_state(config).values["ticket_id"])

幂等：重复恢复不重复创建

恢复可能被重试。创建前先按 idempotency_key 查一次， 已存在就返回原工单。这样即使节点重新进入，也不会多建一张。

场景结果
正常确认创建一张工单
拒绝不创建，返回空 ticket_id
恢复重试查到原工单，返回同一个 id
换 thread找不到暂停点，需从头

陷阱与窍门

创建放在 interrupt 之前

你会看到还没确认就建了工单，恢复时又建一次。因为节点会重新进入。改成副作用放到 interrupt 之后。

恢复换了 thread

你会看到找不到暂停点。因为中断按 thread 保存。改成同一个 config。

没有幂等键

你会看到重复恢复产生两张工单。因为节点可能重试。改成按业务主键查重。

自检三问

  1. 为什么创建工单必须放在 interrupt 之后？
  2. 恢复时为什么不能换 thread_id？
  3. 幂等键用什么字段最合适？

30 分钟动手练习

  1. 跑一次确认与一次拒绝，观察 ticket_id 差异。
  2. 连续 resume 两次，确认只创建一张工单。
  3. 把 interrupt 前的草稿写库，观察恢复时是否重复写。

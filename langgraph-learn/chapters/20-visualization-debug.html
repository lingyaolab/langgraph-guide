20 · 可视化与调试：把图画出来，再定位问题

图的问题通常不是「代码报错」，而是「它走了你没预料的那条边」。 这一章先教你把图导出，再用 updates / checkpoint 历史定位是哪一步偏了。

读完你能做到

  • 用 get_graph().draw_mermaid() 导出图结构
  • 用 stream_mode="updates" 看每个节点改了什么
  • 用 checkpoint 历史定位「从哪一步开始不对」
  • 建立一套从现象到层的排查顺序

先说为什么：先看结构，再看状态

调试图有两个维度：结构（有哪些节点、边、分支）和状态（每一步改了什么）。 先画结构，能排除「边连错」；再看 updates，能定位「哪个节点改错」。 两个都不看，只盯着最终输出，很难判断问题在哪。

最小可跑：导出 Mermaid

print(graph.get_graph().draw_mermaid())

get_graph main.py:909 返回可绘制的图对象；draw_mermaid() 输出文本， draw_png() 需要额外依赖。

图结构：节点、边与命名空间

你看到说明
__start__ / __end__虚拟入口 / 出口
条件边标签路由函数返回的路径 key
子图节点展开后有独立命名空间
循环回边条件边指回上游

状态调试：updates 与历史

for update in graph.stream(inputs, stream_mode="updates"):
    print(update)

updates 会告诉你「哪个节点返回了什么」。如果某个节点返回的字段不对， 再去看它的输入；输入不对，就继续往上游找。 

for snap in graph.get_state_history(config):
    print(snap.metadata["step"], snap.next, snap.values)

历史从新到旧。找到「第一次出现异常值」的快照，它的前一步通常就是问题节点。

工程实践：三种写法与排查

三种调试视角

print(graph.get_graph().draw_mermaid())          # 结构
for u in graph.stream(inputs, stream_mode="updates"): print(u)  # 路径
for s in graph.get_state_history(config): print(s.metadata, s.next)  # 状态
现象先看
走了意外分支结构图 + 路由函数输入
某字段被覆盖updates 里哪个节点写了它
恢复后状态不对checkpoint 历史第一次偏离
子图报错事件命名空间 / 子图历史

再深入一点：实现细节与边界

从事件看执行顺序

for event in graph.stream_events(inputs, version="v2"):
    if event["event"] in ("on_chain_start", "on_chain_end"):
        print(event["name"], event["event"])

stream_events main.py:3703 比 updates 更细，能看到链、模型与工具的进入 / 退出。

四层排查法

层看什么工具
结构节点 / 边 / 分支get_graph().draw_mermaid()
路径走过哪些节点stream_mode="updates"
状态每步 state 变化get_state_history
外部模型 / 工具 / 网络trace / 日志

不要只依赖最终输出

最终输出正确不代表中间路径正确。测试要断言路径； 调试要找到「第一次偏离预期」的节点，而不是从最后倒推。

陷阱与窍门

只看最终 state

你会看到知道错了但不知道哪步错。因为中间状态被覆盖。改成用 updates 或 checkpoint 历史。

把 draw_png 当必选

你会看到缺少 graphviz 依赖。因为PNG 渲染需要额外安装。改成先用 Mermaid 文本，或把文本贴进支持 Mermaid 的编辑器。

子图报错但父图看不出

你会看到父图只显示子图节点失败。因为命名空间被折叠。改成看事件里的 checkpoint_ns 或子图自己的历史。

自检三问

  1. 图结构调试与状态调试分别解决什么问题？
  2. updates 与 values 哪个更适合定位「谁改错了」？
  3. 子图问题为什么要看命名空间？

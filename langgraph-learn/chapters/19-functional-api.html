19 · 函数式 API：@entrypoint 与 @task

不是所有流程都适合画成图。LangGraph 还提供函数式 API： 用 @entrypoint 包住一段普通 Python，用 @task 标记可重试 / 可缓存的步骤。 这一章讲它和 StateGraph 的边界。

读完你能做到

  • 用 @entrypoint 和 @task 写一个可持久化的工作流
  • 说清函数式 API 与 StateGraph 的职责差异
  • 知道什么时候该从函数式迁移到显式图
  • 用 get_config 读取 thread_id 等运行时配置

先说为什么：有些流程就是一段代码

如果流程是「取数据 → 调模型 → 写结果」这种线性结构，画图会增加很多样板代码。 函数式 API 让你保留普通 Python 的控制流，同时获得 checkpoint、重试与流式能力。 当分支、循环、并行、多 Agent 变复杂时，再迁移到 StateGraph。

最小可跑：一个 entrypoint + 两个 task

from langgraph.func import entrypoint, task


@task
def fetch(url: str) -> str:
    return f"content of {url}"


@task
def summarize(text: str) -> str:
    return text[:20]


@entrypoint()
def workflow(url: str) -> str:
    raw = fetch(url).result()
    return summarize(raw).result()


print(workflow.invoke("https://example.com"))

@task __init__.py:110 把函数包成可单独调度、可重试、可缓存的步骤； @entrypoint __init__.py:262 把整段工作流暴露成可 invoke / stream 的对象。

逐行解读：result 与 checkpoint

fetch(url).result() 会立即执行并拿结果；如果工作流挂了 checkpointer， 每个 task 的结果都会写入 checkpoint，恢复时不会重复执行已完成的 task。 这也是函数式 API 和「普通 async 函数」最大的区别。 

from langgraph.checkpoint.memory import InMemorySaver

workflow = workflow.compile(checkpointer=InMemorySaver())
config = {"configurable": {"thread_id": "u-1"}}
workflow.invoke("https://example.com", config)

运行时配置：get_config

在 entrypoint 内部可以用 get_config() config.py:17 读取当前线程、用户与自定义配置。不要从全局变量拿请求上下文。 

from langgraph.config import get_config


@entrypoint()
def workflow(url: str) -> str:
    cfg = get_config()
    thread_id = cfg["configurable"]["thread_id"]
    return f"{thread_id}:{url}"

函数式 API vs StateGraph

维度函数式 APIStateGraph
控制流普通 Python if / for节点 + 边
状态函数参数与返回值显式 State + reducer
可视化弱强
中断 / 恢复支持 task 级节点级，更细
适合线性、轻量工作流分支、并行、多 Agent

工程实践：三种写法与排查

task 的三种用法

# 顺序
a = fetch(url).result()
b = summarize(a).result()

# 并行
a, b = (fetch(u) for u in urls)
results = [x.result() for x in (a, b)]

# 带重试
@task(retry_policy=RetryPolicy(max_attempts=3, retry_on=TimeoutError))
def fetch(url: str) -> str: ...
现象原因改法
恢复后重复执行没有 checkpointer / task 不幂等挂 checkpointer + 幂等键
task 不并行用了 .result() 立刻取先收集 task 再取结果
读不到 thread_id用了全局变量get_config()
流程越写越复杂分支超过两三层迁移到 StateGraph

再深入一点：实现细节与边界

task 的重试与缓存

@task 支持重试与缓存，但只对「可重放」的步骤有意义。 发邮件、扣款这类副作用要加幂等键，或放到 entrypoint 末尾。 

@task(retry_policy=RetryPolicy(max_attempts=3, retry_on=TimeoutError))
def fetch(url: str) -> str:
    return client.get(url).text

函数式与图混用

一个 entrypoint 里可以调用编译后的子图，反之也可以把 entrypoint 当成图的一个节点。 混用时先想清楚 checkpoint 归谁管，不要两层各写一份。

边界

  • 需要可视化、并行 fan-out、复杂 HITL 时，显式图更清楚。
  • 函数式 API 的恢复粒度是 task，不是节点。
  • 不要在 entrypoint 里用全局变量保存请求上下文。

陷阱与窍门

在 task 里写不可重放的副作用

你会看到恢复后重复发邮件。因为task 可能重试。改成加幂等键，或把副作用放到 entrypoint 末尾。

以为 task 会自动并行

你会看到顺序执行。因为.result() 是阻塞取结果。改成需要并行时显式 asyncio.gather 或改用 Send。

复杂流程硬用函数式

你会看到if/else 套得很深，无法可视化。因为控制流回到了代码。改成分支超过两三层就迁移到 StateGraph。

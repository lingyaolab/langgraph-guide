14 · 多 Agent：Supervisor、Swarm 与 handoff

多 Agent 不是「多个模型一起跑就更强」。它解决的是职责隔离： 每个 Agent 有自己的提示词、工具与上下文，由一个路由层决定谁接手。 这一章讲三种拓扑与它们的失败边界。

读完你能做到

  • 用 Supervisor 模式让一个路由 Agent 决定交给哪个 Worker
  • 用 Command(goto=...) 做 handoff，把控制权转给另一个节点
  • 说清共享 state 与独立 state 的边界
  • 估算多 Agent 的 token 成本与失败面

先说为什么：多 Agent 不是并行加速

如果两个 Agent 做同一件事，多 Agent 只会让成本翻倍。 它真正有用的场景是：不同角色需要不同工具 / 提示词 / 权限， 或者需要「一个负责规划、一个负责执行、一个负责审查」。

最小可跑：一个 Supervisor 两个 Worker

from typing import Literal, TypedDict

from langgraph.graph import END, START, StateGraph


class State(TypedDict):
    task: str
    next: str
    result: str


def supervisor(state: State) -> dict:
    if "代码" in state["task"]:
        return {"next": "coder"}
    return {"next": "researcher"}


def coder(state: State) -> dict:
    return {"result": "代码已完成", "next": "supervisor"}


def researcher(state: State) -> dict:
    return {"result": "资料已整理", "next": "supervisor"}


def route(state: State) -> Literal["coder", "researcher", "supervisor"]:
    return state["next"]  # type: ignore[return-value]


builder = StateGraph(State)
builder.add_node("supervisor", supervisor)
builder.add_node("coder", coder)
builder.add_node("researcher", researcher)
builder.add_edge(START, "supervisor")
builder.add_conditional_edges("supervisor", route, ["coder", "researcher", "supervisor"])
builder.add_conditional_edges("coder", route, ["supervisor"])
builder.add_conditional_edges("researcher", route, ["supervisor"])

graph = builder.compile()
print(graph.invoke({"task": "写一段排序代码", "next": "", "result": ""}))

这是一个最小 Supervisor：路由 Agent 只看任务，Worker 干完把 next 设回 supervisor。真实实现里，路由决策通常由模型做，而不是字符串匹配。

三种拓扑：路由、交接、团队

拓扑控制权适合风险
Supervisor中心路由一直掌握任务分派、审查路由成为瓶颈
Swarm / handoff控制权在 Agent 间转移多轮协作、接力容易循环、难追踪
Team / 固定流水线图结构决定顺序稳定流程不够灵活

handoff：控制权怎么转

handoff 的本质是一个节点返回 Command(goto="另一个 Agent")， 同时更新共享 state 里「现在谁负责」。它不需要中心路由， 但需要严格的退出条件与最大轮次。 

from langgraph.types import Command


def researcher(state: dict) -> Command:
    return Command(
        update={"owner": "coder", "notes": "资料在这里"},
        goto="coder",
    )

Command types.py:843 同时改 state 与跳转；这比「先写 state，再靠条件边读」少一次路由决策。

成本与失败边界

  • 每个 Agent 都有自己的系统提示与上下文，token 成本按 Agent 数叠加。
  • 共享 messages 会让每个 Agent 看到全部历史；独立 state 则需要显式传递。
  • handoff 循环必须有最大轮次或明确终止条件，否则会烧穿预算。
  • 路由错误比单 Agent 更难发现：先看「谁最后改了 state」，再看路由日志。

工程实践：三种写法与排查

中心路由与交接

def supervisor(state: dict) -> dict:
    return {"next": "researcher" if state["needs"] == "facts" else "coder"}
def researcher(state: dict) -> Command:
    return Command(update={"owner": "coder"}, goto="coder")
现象原因改法
两个 Agent 踢皮球没有轮次上限加 rounds / END
上下文爆炸共享全部 messages只共享必要字段
路由错提示词模糊用结构化输出 / 规则
成本翻倍把多 Agent 当并行需要并行用 Send

再深入一点：实现细节与边界

用 Command 做 handoff

from langgraph.types import Command


def researcher(state: dict) -> Command:
    return Command(
        update={"owner": "coder", "notes": state.get("notes", "") + "\n资料"},
        goto="coder",
    )

Supervisor 的轮次上限

class State(TypedDict):
    task: str
    owner: str
    rounds: int


def supervisor(state: State) -> dict:
    if state["rounds"] >= 6:
        return {"owner": "END"}
    return {"owner": "researcher", "rounds": state["rounds"] + 1}

共享状态的边界

共享什么建议
任务目标、验收标准共享
每个 Agent 的完整推理不共享，容易污染
工具调用结果按需摘要后共享
用户偏好放 Store，不进 messages

陷阱与窍门

两个 Agent 共享全部 messages

你会看到上下文迅速膨胀、角色混淆。因为每个 Agent 都看到别人的完整推理。改成只共享必要字段，或给每个 Agent 单独的 messages 通道。

handoff 没有终止条件

你会看到两个 Agent 互相踢皮球。因为没有最大轮次或完成判定。改成加 round 计数与 END 路径。

把多 Agent 当并行加速

你会看到成本翻倍但延迟没降。因为多数拓扑是串行委派。改成需要并行时用 Send / 并行节点，不要假装多 Agent 是并行。
